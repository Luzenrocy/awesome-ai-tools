# Public foundations for the style baseline

These sources are used as design inputs, not as copied templates. Follow a project or external-skill contract first, then apply the smallest applicable pattern.

## Requirements and design

- [IEEE/ISO/IEC 29148-2018](https://standards.ieee.org/ieee/29148/6937/) defines requirements engineering processes and the characteristics of good requirements. Use it to justify stable IDs, traceability, quality attributes, and lifecycle validation.
- [NASA Appendix C: How to Write a Good Requirement](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/) gives practical checks for clear, singular, verifiable requirements. Use it to challenge vague or compound statements.
- [NASA SWE-034 Acceptance Criteria](https://swehb.nasa.gov/spaces/7150/pages/16450634/SWE-034%2B-%2BAcceptance%2BCriteria) and [NASA SWE-055 Requirements Validation](https://swehb.nasa.gov/spaces/7150/pages/16449673/SWE-055%2B-%2BRequirements%2BValidation) support explicit acceptance and validation evidence.
- [NASA SWE-109 Software Requirements Specification](https://swehb.nasa.gov/spaces/7150/pages/16449740/SWE-109%2B-%2BSoftware%2BRequirements%2BSpecification) and [NASA SwDD](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695674/5.13+-+SwDD+-+Software+Design+Description) are useful public examples of requirements and design-document boundaries.
- [IEEE 1016 Software Design Descriptions](https://standards.ieee.org/ieee/1016/4502/) is a reference point for documenting software design views and decisions.
- [ISO/IEC/IEEE 26514 user information](https://www.iso.org/obp/ui?_escaped_fragment_=iso:std:iso-iec-ieee:26514:ed-1:v1:en) is a reference for user-information planning and content.
- [ISO/IEC/IEEE 15289:2019](https://www.iso.org/cms/%20render/live/en/sites/isoorg/contents/data/standard/07/49/74909.html) provides a lifecycle view of information items and their purposes. Use it to choose a document shape without forcing every document into one template.

## Technical writing and product documents

- [Google developer documentation style guide](https://developers.google.com/style) emphasizes clear, consistent, audience-aware technical documentation. Its [documents guidance](https://developers.google.com/tech-writing/one/documents) supports stating audience, scope/non-scope, prerequisites, and a summary early.
- [Google style highlights](https://developers.google.com/style/highlights) supports sentence-case headings, active voice, numbered procedures, descriptive links, code formatting, and unambiguous dates.
- [GitHub content design principles](https://docs.github.com/en/contributing/writing-for-github-docs/content-design-principles) prioritizes user needs, clarity, correctness, consistency, and just-enough documentation.
- [Atlassian PRD template](https://www.atlassian.com/software/confluence/templates/product-requirements) is a public product-document example that connects purpose, features, user stories, priority, ownership, and release tracking.
- [NASA ICON Project Requirements](https://explorers.larc.nasa.gov/2023ESE/pdf_files/4_ICON%20L2%20Project%20Requirements.pdf) and [Fermilab Functional Requirements Specification](https://beamdocs.fnal.gov/AD/DocDB/0070/007085/002/FRS-Booster%20Intensity-BD7085.pdf) are public examples of formal requirement-document organization and traceability.

The council uses these sources to establish a professional baseline. It does not claim that any one source is a mandatory organizational standard; a project-specific contract always wins.
